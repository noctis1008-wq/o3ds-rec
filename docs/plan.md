# o3ds-rec 設計・計画書

目的: **旧3DS（初期型3DS / 3DS LL / 2DS）で、偽トロ（キャプチャ基板）なしに高画質・高フレームレートでゲーム映像を記録する。**

## 1. 現状分析（なぜ NTR viewer では足りないか）

| 項目 | 事実 |
|---|---|
| 旧3DS で NTR/NTR-HR | 作者自身が「旧3DS は 3〜7fps」と明記。公式には New 3DS 専用 |
| New 3DS で NTR-HR | 60〜90fps（18Mbps）まで改善済み。差は CPU（New: 804MHz×4コア / 旧: 268MHz×2コア） |
| HzMod / ChirunoMod | 旧3DS対応だが上画面のみ・低fps・不安定 |
| 旧3DS の Wi-Fi | 802.11b/g。生映像（上画面 RGB565 30fps ≒ 46Mbps）はそもそも通らない |

**結論: 遅さの原因は PC 側ビューアではなく、3DS 側で JPEG 圧縮する CPU 時間。** ビューアをいくら改良しても fps は上がらない。Wi-Fi で送るには圧縮が必須で、旧3DSの CPU では圧縮が間に合わない、という構造的な詰みがある。

## 2. 方針: SD カードへ「ほぼ無圧縮」で書く

圧縮をやめれば CPU はほとんど要らない。代わりに必要なのは SD の書き込み帯域。

- 方式: 前フレームと比べて**変化したライン（縦1列）だけを生データで書く**（docs/format.md）
- CPU 負荷: `memcmp` + `memcpy` 程度。JPEG の数十分の一
- 画質: **完全ロスレス**（ゲームの描画そのもの）
- 変換: PC で `3dr2mp4.py` が MP4（x264）または FFV1 可逆に変換。整数倍拡大も可（解説動画向け）

### 必要な書き込み速度（最悪ケース = 毎フレーム全画面が変化）

| 形式（上画面 400×240） | 30fps | 60fps |
|---|---|---|
| RGB565 | 5.5 MB/s | 11.0 MB/s |
| BGR8 / RGBA8→BGR8 | 8.2 MB/s | 16.5 MB/s |
| ＋下画面（RGB565, 毎フレーム変化） | +4.4 MB/s | +8.8 MB/s |

**実測（2026-11-20、旧3DS、docs/bench/）:** SD 連続書き込みは 1MB 単位＋ファイル事前確保で **6.5MB/s** が上限（掲示板の 10〜13MB/s は出ない）。
1MB 単位にまとめて書く方式で、最悪ケース（毎フレーム全画面変化）の録画パイプラインは:

| 形式 | 1フレーム | 差分処理 | 書き込み | 最大fps |
|---|---|---|---|---|
| RGB565 | 187KB | 3.3ms | 27ms | **32fps** |
| BGR8 / RGBA8→BGR8 | 281KB | 5〜7ms | 42ms | **21fps** |

- CPU は余裕（差分処理は1フレーム 3〜7ms）。ボトルネックは SD 書き込み。
- フレーム単位の小さい書き込み（v0.1）は 0.1MB/s まで落ちた。**必ず 1MB 単位にまとめ、ファイルは先に確保する。**
- 書き込みは時々 200ms 前後止まる → 1〜2MB のリングバッファで吸収する。
多くの3Dゲームは 30fps 描画なので、60Hz で見ても半分は「変化なし」で書き込みゼロになる。

### 予想される到達点（仮説・ベンチで検証）

- 上画面 30fps ロスレス: 有望
- 上画面 60fps（2Dゲーム・UI中心で変化が少ない場面）: 有望
- 60fps の3Dゲーム全画面変化: SD 速度次第。足りなければ自動で 30fps に間引く

## 3. 実装の土台

**2026-11-20 変更: Luma3DS の Rosalina に録画機能を入れる方式に切り替えた。** 理由: (1) HOME メニューからゲームまで続けて録りたい（ゲーム内プラグインでは不可）、(2) NTR-HR は旧3DS実機でリモートプレイ開始時にゲームが止まった（録画なしでも再現）、(3) Wi-Fi 不要・画面切り替えに合わせて取り込める。実装: noctis1008-wq/Luma3DS `o3ds-rec` ブランチの sysmodules/rosalina/source/recorder.c。chainload 用 firm として配布し boot.firm は触らない。

### （旧）NTR-HR（xzn/ntr-hr）の旧3DSモードを改造

NTR-HR には既に旧3DS向けビルド（`o3ds` / `mem3` feature）があり、画面取得の仕組みはそのまま使える。

| 使う部分 | 場所 |
|---|---|
| 画面キャプチャ（DMA でフレームバッファを取得） | `source/nwm_rs/src/entries/thread_screen/vars.rs` の `capture_screen` / `try_capture_screen` |
| GPU レジスタから形式・ストライド・アドレス取得 | 同 `update_gpu_regs` |
| 音声キャプチャ（DSP） | `source/nwm_rs/src/entries/thread_audio.rs` |
| SD への書き込み例（fs:USER ハンドル） | `source/boot/main_boot.c`、`source/rt.c` |
| X+Y メニュー | `source/menu/rp_menu.c` / `cfg_menu.c` |

改造内容:
1. キャプチャ後、JPEG エンコーダに渡す代わりに `core/rec_core.c` で行差分化
2. 書き込み専用スレッド＋リングバッファ（SD の一時的な詰まりを吸収）で `FSFILE_Write`
3. X+Y メニューに「SD録画 開始/停止」、録画中は LED か画面隅で表示
4. 3.5GB で自動分割、開始・終了 tick と EOS を記録

## 5. リスクと対策

| リスク | 対策 |
|---|---|
| ダウンロード版ゲームは SD から読み込むため帯域を取り合う | まずカード版で検証。ベンチの「1回の最大待ち」を見てリングバッファ量を決める |
| 旧3DS は nwm プロセスのメモリが少ない（大容量メモリ使用ゲーム＝mem3） | フレーム2枚＋リングバッファ 1〜2MB に抑える。mem3 ゲームは当面対象外 |
| SD の詰まりでフレーム落ち | 書き込みスレッド分離、溢れたら古いフレームを捨てて記録（tick があるので変換時に時間は正しく埋まる） |
| 電池・発熱 | 長時間録画時は AC アダプタ推奨と明記 |
| 音声キャプチャ不安定 | 最悪はイヤホン端子から PC で録音し、変換ツールで波形同期 |

## 6. 検討して見送った案

- **PC 側ビューアの改良のみ**: ボトルネックが 3DS 側なので効果なし
- **Wi-Fi で無圧縮/軽圧縮送信**: 旧3DS の無線帯域（実効 十数Mbps 以下）に入らない
- **入力記録→エミュレータで再生**: 実機とエミュの挙動差で数分でズレる。乱数・時間依存のゲームで破綻
- **ARM9 や DSP に圧縮させる**: ARM9 はファイルアクセス（Process9）担当、DSP はゲーム音声担当で横取りは危険
